### 무엇을 만드나요?

> D435i Color → HSV·Contour → 중심 오차·시각·검출 여부 → 제한 제어 → Raspberry Pi·OpenCR → 다이나믹셀 → 카메라 회전 → 다음 영상. 정렬 Depth는 유효 거리 확인에 사용하며 기본 추적은 수평 1축이다.
> 

D435i를 다이나믹셀 회전축에 장착하여 영상 오차가 구동 결과로 줄어드는 폐루프를 완성한다. 이동 베이스·집기·운반을 요구하지 않는다. 핵심은 실제 추적, 소실·통신 중단 시 정지, 정해진 조건의 복귀이다.

| 구분 | 제작 범위 |
| --- | --- |
| 필수 | D435i Color 기반 단일 색상 목표 1개를 대상으로 HSV·Contour, Lyrical 인지·제어 연결, 다이나믹셀 수평 1축 P 추적, 목표 소실·통신 단절 정지와 재등장 복귀를 구현한다. 정렬 Depth·CameraInfo의 수집과 유효성 확인을 기록하되 정밀 3D 보정을 기본 완료 조건으로 추가하지 않는다. |
| 선택 | 장비가 준비된 경우 2축 추적, Depth 기반 작업 거리 검사·3D 역투영, 데드밴드·필터 비교, 고정 bag 회귀 비교를 선택한다. Isaac ROS 5.0 GPU Resize·Isaac Sim/Lab·D435i IMU·딥러닝 학습은 선택 확장이다. 기본 수평 1축 실물 추적을 먼저 완성한다. |

앞선 강의의 코드를 재사용하되 연결과 검증 결과를 남깁니다.

### 프로젝트 시작 전 준비

- 영상·인지 노드는 Ubuntu 24.04 + Lyrical PC에서 실행한다. OpenCR 빌드·업로드·시리얼 수신은 기존 원칙대로 SSH 접속한 Raspberry Pi에서 수행한다. PC와 Pi 사이의 명령 브리지를 별도 검증하며 SSH만으로 ROS 메시지가 전달된다고 가정하지 않는다. Pi도 Ubuntu Server 24.04 64비트(arm64)와 ROS 2 Lyrical로 통일하고 ROS_DOMAIN_ID·RMW·DDS 통신을 확인한다.
- 모터 모델·ID·통신 속도·프로토콜은 실제 장비에서 확인합니다. 다른 팀의 값을 복사하지 않습니다.
- OpenCR과 모터의 연결·전원·고정 상태를 확인하고, 실제 기구에 맞는 회전 범위와 낮은 속도 상한을 정합니다.
- D435i 시리얼·펌웨어·SDK·ROS wrapper 버전, USB 속도, 실제 Color·Depth 프로파일, encoding·CameraInfo·frame_id·stamp를 기록한다. Lyrical에서 wrapper의 빌드·실행 호환성을 따로 확인한다.
- 제어 프로그램과 시리얼 모니터가 같은 OpenCR 포트를 동시에 점유하지 않도록 합니다.
- USB 시리얼 또는 이미 구성된 micro-ROS 중 하나를 사용합니다. 명령 형식·단위·주기·정지 규칙을 문서화합니다.
- SSH 환경에서는 GUI 창이 필수가 아닙니다. 마스크·검출 결과를 이미지나 영상으로 저장하여 PC에서 확인해도 됩니다.
- **제어 통신이 끊겨도 마지막 속도로 계속 회전하면 안 됩니다.** 라즈베리파이뿐 아니라 OpenCR 또는 모터 측에도 통신 타임아웃 정지를 적용하고 시험합니다.

# 2️⃣ 프로젝트 목표와 취업 역량 연결

### **⭐️ 프로젝트 목표**

- 모듈 ①의 OpenCR·다이나믹셀 제어를 이용하여 실제 장비의 방향·속도·각도 제한과 정지 조건을 적용합니다.
- 모듈 ③·④의 카메라·OpenCV 학습을 바탕으로 HSV·Contour 검출과 정규화된 중심 오차를 계산합니다.
- ROS2 노드·토픽 학습을 활용하여 인지와 제어를 분리하고 메시지·단위·시간·실패 규칙을 정의합니다.
- Kp 변화와 목표 소실·통신 중단 시험의 결과를 원본 데이터로 설명하고, bag과 실행 문서로 다른 팀원의 재현을 지원합니다.
- Issue·PR·코드 리뷰를 통해 4명이 구현과 검증을 나누고 각자의 기여를 증빙합니다.

완료 후에는 카메라 입력부터 모터 추적·안전 정지·성능 분석까지 이어지는 시스템을 구현하고, 측정 결과와 팀 협업 기록을 근거로 설계 판단을 설명할 수 있어야 합니다.

### **취업 역량과 프로젝트 수행 작업의 연결**

| 순위 | 취업에 필요한 역량 | 이 작업을 잘 수행해야 하는 이유 |
| --- | --- | --- |
| 1 | 센서 데이터 처리·컴퓨터 비전 | 현실의 센서 입력은 조명·배경·가림에 따라 불완전해지므로, HSV·마스크·잡음 제거·Contour·대상 선택·중심 계산을 같은 기준으로 구현하고 정상·미검출·가림 장면까지 검증해야 실제 환경에서 사용할 수 있는 인지 역량을 증명할 수 있습니다. |
| 2 | ROS2 기반 시스템 통합·인터페이스 설계 | 인지 결과가 제어 노드에서 다르게 해석되면 로봇은 잘못 움직이므로, `/target`의 좌표·면적·시간·오차 부호·단위를 명확히 정하고 QoS·주기·실패 규칙까지 검증해야 여러 노드와 담당자가 함께 개발할 수 있는 통합 역량을 보여줄 수 있습니다. |
| 3 | 제어·하드웨어 통합 | 검출 결과가 실제 모터의 안전한 움직임으로 이어져야 Physical AI 시스템이 완성되므로, OpenCR·다이나믹셀의 실제 ID·baud·방향·전원을 확인하고 중심 오차 기반 P 제어에 속도·각도 제한·데드밴드를 적용한 뒤 Kp를 동일 조건에서 비교해야 하드웨어 제약을 반영하는 제어 역량을 증명할 수 있습니다. |
| 4 | 안전 제어·실패 복구·검증 | 센서 소실이나 통신 장애 때 계속 움직이는 시스템은 현업에 투입할 수 없으므로, IDLE·TRACKING·LOST 상태와 정지 규칙을 구현하고 정상 추적·가림 후 복귀·통신 중단을 반복 시험하여 FPS·검출률·RMSE·복구 성공률·복구 시간을 근거로 판단해야 안전성과 검증 역량을 증명할 수 있습니다. |

### **취업·포트폴리오에서 반드시 증명해야 할 결과**

- 센서 입력부터 모터 구동까지의 구조와 본인 담당 모듈을 연결해 제시해야 합니다. 그래야 단일 기능 구현이 아니라 인지·통합·제어를 완성한 경험으로 평가받을 수 있습니다.
- 미검출·통신 중단·복구 실패에서도 정지한 기록을 남겨야 합니다. 그래야 정상 시연만으로는 확인할 수 없는 안전 제어와 실패 대응 역량을 증명할 수 있습니다.
- Kp 비교와 FPS·검출률·RMSE·복구 결과를 원본 데이터·산식·시험 조건과 함께 남겨야 합니다. 그래야 결과를 임의로 선택한 것이 아니라 측정에 근거해 설계 판단을 내렸다는 것을 보여줄 수 있습니다.
- 코드·설정·로그·bag·README·PR·리뷰를 서로 연결해야 합니다. 그래야 다른 사람이 같은 조건에서 실행하고 결과를 확인할 수 있는 재현 가능한 개발 역량을 증명할 수 있습니다.
- 수행하지 않은 기능과 측정하지 않은 결과를 구분하고 한계·개선 방향을 기록해야 합니다. 그래야 실제 검증 범위를 과장하지 않고 기술적 판단과 문제 인식 능력을 보여줄 수 있습니다.

대상은 배경과 색상이 구분되는 카드·공·블록 중 하나를 선택할 수 있습니다. 소재가 달라도 단일 색상 목표 1개·수평 1축 추적과 동일한 검증·산출물 기준을 적용합니다. 아래 문제 1~5를 하나의 시스템으로 완성합니다.

- **문제 1 — HSV·Contour 검출 파이프라인**
    
    #### 구현 내용
    
    1. 배경과 구분되는 단일 색상 목표 1개를 선정하고 사진을 남깁니다.
    2. 영상 → HSV 변환 → 색상 마스크 → 잡음 제거 → 컨투어 → 대상 선택 → 중심 계산을 구현합니다.
    3. HSV 범위·최소 면적·해상도를 설정 파일로 분리하고 여러 후보 중 선택 규칙을 정합니다.
    4. 원본 위에 컨투어·목표 중심·영상 중심을 표시합니다. 미검출 때 이전 좌표를 새 목표로 재사용하지 않습니다.
    5. 목표가 잘 보이는 장면·없는 장면·일부 가려진 장면을 같은 설정으로 확인합니다.
    
    정규화 오차는 ex=(cx-W/2)/(W/2), ey=(cy-H/2)/(H/2)입니다. 
    오른쪽·아래쪽을 양수로 정하며, W·H는 실제 프레임 크기입니다. 
    면적비는 contour_area/(W×H)입니다.
    
    #### 결과물과 보고서
    
    세 장면의 원본·마스크·검출 이미지, 실제 설정, 검출·미검출 기록을 제출합니다. 
    HSV 범위를 정한 근거, 배경 오검출을 줄인 조건, 미검출 전달 방식을 설명합니다.
    
    **심화:** 조명 또는 거리 조건 하나를 바꾸고 검출률·처리 속도의 변화를 비교합니다.
    
- **문제 2 — 인지·제어 노드 연결**
    
    #### 기본 인터페이스
    
    | 항목 | 규약 |
    | --- | --- |
    | 목표 토픽 | /target · geometry_msgs/msg/PointStamped |
    | point.x / point.y | 정규화 중심 오차 ex / ey |
    | point.z | 면적비 · 0=미검출, 이때 x·y로 제어하지 않음 |
    | header.stamp | 원본 영상 시각 유지 · 촬영 시각을 모르면 영상 수신 시각임을 명시 |
    | 발행 | 영상 처리마다 발행 · 정상 영상의 미검출은 z=0 발행 |
    | QoS | best-effort, depth 1부터 적용 · 구독 측 호환 확인 |
    | 상태 | /tracking_status 등 팀이 정한 토픽과 상태 값 |
    | 모터 명령 | 위치/속도 방식, 단위·부호·주기·정지 명령 명시 |
    | 타임아웃 | 마지막 신선한 입력 수신 후 0.5초 기본 · 변경 이유 기록 |
    
    PointStamped는 이 과제의 목표 정보 전달 규약이며 일반적인 3차원 위치로 해석하지 않습니다.
    
    #### 구현 내용과 확인 입력
    
    노드·연결 구조도와 인터페이스 표를 작성하고, **모터 출력을 끈 상태**에서 다음 입력을 확인합니다.
    
    | 입력 | 기대 결과 |
    | --- | --- |
    | x=0, z>0 | 중심에서 불필요한 회전 없음 |
    | x=+0.4, z>0 | 오른쪽 오차를 줄이는 명령 |
    | x=-0.4, z>0 | 반대 방향 명령 |
    | z=0 | 이전 목표를 계속 쫓지 않고 정지 |
    | 발행 중단 | 타임아웃 감지 후 정지 |
    
    미검출과 통신 중단을 구분합니다. 
    카메라가 멈췄는데 이전 영상에 새 시각을 붙여 정상 입력처럼 보내면 안 됩니다.
    
    #### 결과물과 보고서
    
    구조도·인터페이스 표·다섯 입력의 명령과 상태 로그를 제출합니다. 
    부호가 반대일 때의 현상, 미검출과 토픽 침묵의 차이, 노드별 책임을 설명합니다.
    
    **심화:** 인터페이스를 구현과 일치하게 완성합니다. 여유가 있으면 /search 액션의 요청·진행·성공/실패·취소를 연결할 수 있으며, 액션 자체는 기본 필수가 아닙니다.
    
- **문제 3 — 객체 중심 기반 추적 제어**
    
    #### 구현 내용
    
    1. 추적을 끈 상태에서 제한된 범위의 작은 명령으로 모터 방향을 확인합니다.
    2. 오른쪽 목표에 대한 명령이 실제 영상의 오차를 줄이는지 확인하여 부호를 정합니다.
    3. P 제어부터 구현합니다. 속도형은 command = clamp(direction × Kp × ex, -speed_limit, +speed_limit)를 사용할 수 있습니다.
    4. direction은 장착에 따라 +1 또는 -1이며 Kp·속도 명령의 단위를 적습니다. 속도를 위치로 적분한다면 실제 경과 시간 dt를 사용합니다.
    5. 속도 상한·회전 범위·중심 데드밴드를 설정합니다. 범위 끝에서 바깥 방향으로 계속 명령하지 않습니다.
    6. Kp 두 값을 같은 대상·거리·해상도·동작 순서로 비교합니다. 작은 값부터 시작하고 다른 조건은 유지합니다.
    7. 오차·명령·상태를 시간과 함께 저장하고 비교 그래프를 만듭니다.
    
    #### 권장 시험
    
    왼쪽 3초 정지 → 중앙 3초 → 오른쪽 3초 → 중앙 3초. 바닥이나 배경에 위치 표시를 붙여 반복 조건을 맞추고 **Kp 설정별 최소 3회** 반복합니다. 달라진 조건은 기록합니다.
    
    모터가 반대로 움직이거나 멈추면 Kp부터 키우지 않습니다. 검출 → 오차 부호 → 명령 → 응답 순서로 확인합니다. 영상 지연이 크면 높은 Kp가 진동을 늘릴 수 있습니다.
    
    #### 결과물과 보고서
    
    두 Kp·제한값·시험 조건, 설정별 CSV·오차 그래프, 실제 추적 영상을 제출합니다. 최종 설정 선택 근거와 반응 속도·흔들림의 차이를 설명합니다. 모터 위치를 측정하지 않았다면 명령을 실제 위치처럼 표시하지 않습니다.
    
    **심화:** 추적 오차를 정량 비교합니다. 데드밴드나 필터를 바꾼다면 하나씩 변경하여 효과를 구분합니다.
    
- **문제 4 — 성능 측정과 목표 소실 복구**
    
    #### 구현 내용
    
    1. `IDLE`·`TRACKING`·`LOST` 상태와 각 상태의 전이 조건을 구현합니다.
    2. 목표를 미검출하거나 인지 입력 타임아웃이 발생하면, 이전 속도를 유지하지 않고 검증된 정지 명령을 실행합니다.
    3. 신선한 목표가 연속 3프레임 검출되면 제한된 명령으로 `TRACKING` 상태를 재개합니다.
    4. 제어 프로그램 또는 통신이 중단되어도 OpenCR 또는 모터 측에서 안전하게 정지하도록 통신 타임아웃을 구현하고 확인합니다.
    5. 정상 추적, 가림 후 재등장, 인지 입력 중단, 제어 통신 중단의 상태·명령·시간을 기록할 수 있도록 로그를 구성합니다.
    
    #### 상태와 정지 규칙
    
    | 상태 | 조건 | 동작 |
    | --- | --- | --- |
    | IDLE | 시작 전 또는 명시적 중지 | 새 추적 명령을 내보내지 않음 |
    | TRACKING | 신선한 입력에서 목표 검출 | 제한 범위 안에서 추적 |
    | LOST | 미검출 또는 입력 타임아웃 | 검증된 정지 명령, 이전 속도 유지 금지 |
    | TRACKING 복귀 | 신선한 목표 연속 3프레임 검출을 기본으로 사용 | 제한된 명령으로 추적 재개 |
    
    미검출 첫 프레임부터 움직임을 정지시키고, 상태 표시에는 짧은 유예를 둘 수 있습니다. 유예·복귀 조건은 설정과 보고서에 적습니다. 위치형은 목표 갱신을 멈추는 것만으로 정지한다고 가정하지 말고 실제 정지를 확인합니다.
    
    기본 복구는 **현재 시야 안에 다시 들어온 목표를 재검출하여 추적 재개**하는 것입니다. 시야 밖 목표를 찾는 스캔 탐색은 선택 심화입니다. 시야 내 재검출을 시야 밖 자동 탐색 성공으로 보고하지 않습니다.
    
    #### 필수 시험
    
    | 시험 | 횟수·조건 | 기록 |
    | --- | --- | --- |
    | 정상 추적 | 동일 조건에서 30초 이상 | 처리 FPS·검출률·중심 오차 |
    | 가림 후 재등장 | 약 2초 가림 후 현재 시야 안에 재등장, 5회 | 정지·복귀 여부·복귀 시간 |
    | 인지 입력 중단 | 목표 토픽 발행 중단, 1회 이상 | 타임아웃·정지 기록 |
    | 제어 통신 중단 | 제어 프로그램 종료 등, 1회 이상 | OpenCR/모터 측 타임아웃 정지 |
    
    움직일 수 없는 상태에서 끊김 처리를 먼저 확인한 뒤 실제 회전은 낮은 속도·제한 범위에서 수행합니다. 실패 회차도 통계에 포함합니다.
    
    #### 측정 지표
    
    | 지표 | 계산 | 기록 조건 |
    | --- | --- | --- |
    | 처리 FPS | 처리 완료 프레임 수 / 실제 경과 초 | 카메라 설정 FPS와 구분 |
    | 검출률 | 올바른 검출 / 목표가 실제 보이는 평가 프레임 ×100 | 고르게 고른 최소 30프레임을 사람이 대조, 목록 저장 |
    | 배경 오검출 | 목표 없는 평가 프레임의 잘못된 검출 수 | 최소 10프레임 대조, 검출률과 별도 기록 |
    | 수평 RMSE | sqrt(mean(ex²)) | 검출·TRACKING 구간 사용, 제외 수와 추적 구간 비율 병기 |
    | 복구 성공률 | 재등장 후 3초 이내 TRACKING 복귀 횟수 / 5 ×100 | 3초는 시험 판정 기준이며 일괄 성능 합격선은 아님 |
    | 복구 시간 | TRACKING 복귀 시각 − 목표 재등장 시각 | 실패는 0초가 아닌 실패로 표시 |
    
    노드의 detected=true 비율은 실제 정답 대조 검출률과 다릅니다. RMSE가 작아도 대부분의 시간을 놓쳤다면 좋은 추적이라고 단정하지 않습니다.
    
    지연을 측정한다면 시작·종료 시각과 시계를 정의합니다. 영상 수신→명령 생성 지연과 모터의 실제 반응 시간은 다릅니다. 촬영 시각을 모르면 촬영→구동 지연이라고 쓰지 않습니다.
    
    CSV에는 run_id, time_s, frame_id, detected, ex, ey, area_ratio, state, command, command_unit을 권장합니다. 실제 측정 위치가 있으면 추가하고 추정값과 실측값을 구분합니다.
    
    #### 결과물과 보고서
    
    성능표·원본 로그·평가 프레임 목록과 정답 판정·복구 5회 결과·통신 중단 시험 기록을 제출합니다. 실패 원인이 검출·통신·제어 중 어디에 있는지 근거를 제시합니다.
    
    **심화:** 복구 성공률·시간과 실패 원인으로 강건성을 설명합니다. 자동 SEARCHING을 추가하면 각도·속도·시간 상한과 취소를 적용하고 미발견 시 정지합니다. 시야 밖 탐색은 기본 재등장 시험과 별도 통계로 냅니다.
    
- **문제 5 — bag 재현과 팀 협업**
    
    #### 구현 내용
    
    1. 대표 성공 장면과 소실·복귀 장면을 각각 10~30초 수준으로 기록하고 용량을 확인합니다.
    2. 영상·목표·상태·명령 토픽을 기록합니다. 시리얼 로그는 같은 실행 ID로 연결합니다.
    3. bag의 토픽·메시지 수·기간·해상도·설정·기준 커밋을 남깁니다. 저장 형식에 맞는 메타데이터와 데이터 파일을 함께 보관합니다.
    4. 다음 재현을 수행하며 **실제 모터 출력을 비활성화**합니다.
    
    | 재현 | 수행 내용 | 확인 |
    | --- | --- | --- |
    | 입력 재처리 | bag 영상만 검출기로 전달, /target_replay 등 별도 출력 | 같은 설정에서 검출과 오차 경향 재현 |
    | 결과 재분석 | 저장 목표·상태·명령으로 지표 재계산 | 기존 성능표와 결과 일치 여부 |
    
    재처리할 때 저장된 /target과 새 검출 결과를 같은 토픽에 섞지 않습니다. 실제 토픽 선택·remap 명령을 README에 적습니다. 기록된 목표를 보기만 한 것은 검출기 재처리가 아닙니다.
    
    시간 기준이 필요하면 --clock과 관련 노드의 use_sim_time을 함께 적용합니다. 과거 bag 시각과 현재 벽시계를 섞어 타임아웃·지연을 계산하지 않습니다. 오프라인 입력 재현은 실제 하드웨어 폐루프 시연과 구분합니다.
    
    1. 작성자가 아닌 팀원이 README만 보고 실행합니다. 확인자·날짜·기준 커밋·결과를 남기고 누락된 경로·설정을 수정합니다.
    2. [team.md](http://team.md)에 4인의 역할·기여·Issue·병합 PR·리뷰 링크와 팀장의 최종 통합 확인을 기록합니다.
    
    #### 결과물과 보고서
    
    bag 메타데이터·접근 위치·기록/재생 명령, 재처리 이미지, 재계산 지표, 다른 팀원 실행 기록, 4인 협업 증거를 제출합니다. 입력 재처리와 결과 재분석의 차이를 설명합니다.
    
    **심화:** 고정 bag으로 변경 전후 지표를 재계산하여 회귀 비교를 수행합니다.
    

# 4️⃣ 도전 실습 (선택)

### **도전 실습의 목적과 진행 방식**

필수 구현과 안전 검증을 완료한 팀은 아래 도전 과제 중 하나 이상을 선택하여 수행합니다. 도전 실습은 기능을 무작정 추가하는 것이 아니라, **하나의 조건만 바꾸고 동일한 기준으로 전후 결과를 비교하여 개선 효과와 한계를 검증하는 활동**입니다.

- 선행 조건: 8번 필수 요구사항의 증빙, 안전 정지, 시야 내 재등장 복구, bag 재현을 먼저 완료합니다.
- 선택 방법: 아래 A~E 중 수행할 항목을 팀에서 정하고, 시작 전에 Issue에 담당자·변경 조건·비교 지표·완료 기준을 기록합니다.
- 공통 시험 원칙: 비교 대상 외의 카메라·장비·거리·해상도·시험 시간·반복 횟수는 유지합니다. 조건을 바꾼 경우 변경 전·후를 명시합니다.
- 공통 제출 원칙: 구현 코드·설정 파일·원본 로그·비교표·그래프·실행 영상·실패 기록을 남기고, [report.md](http://report.md)에 수행한 도전 항목과 미수행 항목을 구분합니다.
- 평가 기준: 기능 개수보다 비교 조건의 일관성, 측정 결과의 재현성, 실패 원인 분석, 안전 처리와 설계 판단을 확인합니다.
- 제외 범위: 딥러닝 학습·다중 객체 ID·완전한 PID·새로운 micro-ROS 구성은 도전 실습의 필수 항목이 아닙니다.

#### 도전 A — 환경 변화에 강한 검출 파이프라인

1. 조명 또는 목표물과 카메라 사이의 거리 중 하나만 변경하는 시험 조건을 정합니다.
2. 변경 전·후에 같은 방식으로 검출률과 처리 FPS를 측정합니다. 목표가 보이는 평가 프레임은 각 조건에서 최소 30개를 대조하고, 목표가 없는 프레임은 최소 10개를 대조합니다.
3. HSV 범위·최소 면적·필터 조건을 변경했다면 변경 이유를 기록하고, 기본 설정과 개선 설정을 각각 실행합니다.
4. 결과에는 조건별 검출률·배경 오검출·처리 FPS·실패 장면을 비교하여 포함합니다.
5. 제출: 조건표, 설정 파일 2종, 평가 프레임 목록, 원본 로그, 비교 그래프, 개선 효과와 한계.

#### 도전 B — 인터페이스 완성도와 SEARCHING 동작

1. `/target`의 좌표·면적·타임스탬프·미검출 값과 오차 부호·단위·주기·QoS를 구현과 문서에서 일치시킵니다.
2. 모터 출력을 끈 상태에서 중심 오차 0, 양·음의 오차, 미검출, 토픽 발행 중단을 다시 입력하고 기대한 명령·상태·정지 결과를 확인합니다.
3. 선택적으로 시야 밖 목표를 찾는 `SEARCHING` 상태를 추가합니다. 탐색 방향·속도·최대 각도·최대 시간·취소 조건을 설정하고, 목표 미발견 시 반드시 정지하도록 합니다.
4. `IDLE`·`TRACKING`·`LOST`·`SEARCHING`의 상태 전이와 각 상태의 출력 명령을 표로 작성합니다. 시야 내 재등장 복구와 시야 밖 탐색 성공을 별도 결과로 기록합니다.
5. 제출: 인터페이스 정의서, 상태 전이표, 모의 입력 로그, 탐색 설정, 정상·취소·미발견 정지 시험 기록, 실행 영상.

#### 도전 C — 추적 제어 성능 비교

1. 기본 P 제어를 기준으로 데드밴드 또는 필터 중 하나만 변경할 대상을 선택합니다.
2. 동일한 대상·거리·해상도·이동 순서에서 기본 설정과 변경 설정을 각각 최소 3회 시험합니다.
3. 각 회차의 중심 오차·명령·상태·시간을 저장하고 수평 RMSE·유효 추적 비율·응답 시간 또는 흔들림을 같은 산식으로 계산합니다.
4. 개선 설정이 오차를 줄였더라도 지연·진동·미검출 구간이 늘었는지 함께 확인합니다. 모터 위치를 측정하지 않았다면 명령값을 실제 위치값으로 해석하지 않습니다.
5. 제출: 변경한 파라미터, 시험 조건, 회차별 CSV, 지표 산식, 비교 그래프, 최종 설정 선택 근거와 부작용.

#### 도전 D — 목표 소실 복구의 강건성 검증

1. 기본 가림 후 재등장 시험을 확장하여 복구 성공률과 복구 시간을 계산하고, 성공·실패 회차를 모두 기록합니다.
2. 실패 원인을 검출 실패·입력 타임아웃·제어 통신 중단·복귀 조건 미충족 중 하나 이상으로 분류합니다.
3. 복구 조건 또는 정지 유예를 변경했다면 한 번에 하나의 조건만 변경하고 기본 설정과 비교합니다.
4. 복구 실패 시 이전 속도 유지, 잘못된 목표 추적, 무제한 탐색이 발생하지 않는지 확인합니다.
5. 제출: 회차별 상태·정지·복귀 로그, 복구 성공률·복구 시간 표, 실패 원인 분류, 원본 영상, 개선 전·후 비교와 한계.

#### 도전 E — 고정 bag 기반 회귀 비교

1. 대표 성공·소실 장면의 고정 bag을 기준 버전으로 지정하고, 토픽·메시지 수·기간·설정·기준 커밋을 기록합니다.
2. 검출기·인터페이스·제어 설정 중 하나를 변경한 뒤 실제 모터 출력 없이 같은 bag을 다시 재생합니다.
3. 변경 전·후의 검출률·FPS·RMSE·복구 관련 지표를 같은 코드와 산식으로 다시 계산합니다.
4. 저장된 `/target`과 새 검출 결과를 별도 토픽으로 분리하여, 입력 재처리와 결과 재분석을 구분합니다.
5. 제출: bag 메타데이터와 체크섬, 기준·변경 커밋, 재생 명령, 변경 전·후 지표표·그래프, 회귀 여부와 원인 분석.

### **도전 실습 완료 기준**

- 선택한 도전 과제의 목표·변경 변수·고정 조건·비교 지표를 시험 전에 기록했습니다.
- 수행 작업이 코드·설정·로그·영상·bag 중 해당 증거와 연결되어 있습니다.
- 변경 전·후 결과를 같은 기준으로 계산하고 실패 회차도 포함했습니다.
- 결과가 개선되지 않았더라도 원인과 한계를 기록했습니다.
- 안전 정지와 모터 출력 비활성 상태의 재현 절차를 지켰습니다.
- [report.md](http://report.md)에 선택한 도전 과제, 수행 결과, 미수행 항목, 한계를 기록했습니다.

### **4인 팀 구성과 팀장의 책임**

| 기술 역할 | 주요 책임 |
| --- | --- |
| 인지 | 카메라 입력, HSV·Contour, 미검출 처리, 검출 증거 |
| 제어 | 모터 연결, 오차→명령, 속도·위치 제한, 정지 |
| 통합 | ROS2 인터페이스, 실행 구성, bag 기록·재생 |
| 검증 | 시험 조건, 측정·그래프, 결과 해석·발표 |

팀장은 위 기술 역할 하나를 함께 맡고 **테크리드** 역할을 수행합니다. 

팀장이 모든 코드를 대신 작성하지 않습니다. 
역할은 책임 구분이며 다른 부분을 이해하지 않아도 된다는 뜻이 아닙니다.

#### 팀장이 반드시 해야 하는 일

1. 팀 저장소 생성 또는 생성 요청, 팀원 초대, 권한·main 보호 설정 확인.
2. Issue별 담당자·완료 조건·우선순위 지정 및 진행 상황 확인.
3. 토픽·메시지·단위·주기·설정 경로 등 공통 인터페이스 합의.
4. 팀원 PR의 코드와 실행 증거 리뷰, 수정 요청, 재검토.
5. 승인·리뷰 해결·충돌 해결·검증 후 최종 병합.
6. 최종 main 통합 확인, 미완료 사항 정리, 태그 생성 및 팀 대표 제출.

#### 팀원 전원이 반드시 해야 하는 일

- 각자 GitHub 계정과 작업 브랜치로 구현·시험하고 PR을 작성합니다.
- **본인이 작성한 PR 최소 1건이 병합**되어야 합니다. 팀장도 포함합니다.
- **다른 사람의 PR에 의미 있는 리뷰 최소 1건**을 남깁니다.
- 수정 요청에 답하고 결과를 반영하며, 본인 코드와 검증 근거를 설명합니다.
- [team.md](http://team.md)에 실제 구현·시험 내용, Issue·PR·리뷰 링크를 기록합니다.

**최종 병합은 팀장만 수행합니다.** 팀원은 승인을 받았더라도 직접 병합하지 않습니다. 
**팀장 본인의 PR도 다른 팀원 1명 이상이 검토·승인한 후 팀장이 병합합니다.** 
자기 승인으로 대체하지 않습니다.

팀장 부재 시 대행자 1명과 기간을 [team.md](http://team.md)에 기록하고 필요한 권한만 위임합니다. 
계정·비밀번호·토큰을 공유하여 대신 작업하지 않습니다.

1️⃣

#### 팀 저장소 만드는 방법

**팀 제출 명칭: Lv2_팀명_과제**

(❌ 개인 저장소 4개나 ZIP으로 중복 제출하지 않습니다.) 

1. 팀장이 GitHub에서 SpartaPA 조직의 저장소 목록 → New repository를 선택합니다.
2. Owner가 개인 계정이 아닌 **SpartaPA**인지 확인합니다.
3. Lv2_팀명_과제 형식으로 이름을 정하고 README를 생성합니다. 공개 범위는 조직 운영 기준을 따릅니다.
4. 기본 브랜치를 main으로 설정합니다. 초기 생성 이후 변경은 PR로 반영합니다.
5. Settings의 Collaborators and teams 등 접근 관리 화면에서 팀원 3명을 추가하고 각자 초대를 수락합니다.
6. main 보호 규칙을 적용한 뒤 전원이 clone과 작업 브랜치 push를 확인합니다.
7. 루트 README에 팀명·팀장·4명의 이름/GitHub ID·역할·프로젝트 폴더 링크를 작성합니다.

저장소 생성이나 권한 설정 메뉴가 보이지 않으면 조직 관리자에게 **희망 저장소명·팀원 4명의 GitHub ID·팀장 ID·필요 권한**을 전달하여 요청합니다. 

GitHub에서 한글 저장소명이 허용되지 않거나 이름이 변환되는 경우 실제 저장소는 **Lv2_TeamName_Assignment**처럼 영문으로 생성하고, README 첫 줄에 **Lv2_팀명_과제**를 적습니다. 제출에는 실제 생성된 URL을 사용합니다.

**권한과 main 보호**

| 담당 | 저장소 권한·운영 |
| --- | --- |
| 팀장 | 해당 저장소 Admin을 기본으로 설정 관리·최종 병합 |
| 팀원 | Write로 작업 브랜치 push·PR 작성·리뷰 |
| 조직 관리자 | 정책상 필요한 생성·권한·보호 설정 지원 |

Admin을 팀장에게 부여할 수 없다면 관리자가 규칙을 설정하고 팀장은 병합 가능한 권한으로 운영합니다. **Write 권한만으로 팀원의 main 병합이 자동 금지되는 것은 아닙니다.** 다음 보호 규칙을 함께 적용합니다.

Settings → Branches → main을 대상으로 branch protection을 설정합니다.

- Require a pull request before merging: main 변경은 PR로만 반영.
- Require approvals: 작성자가 아닌 사람의 승인 1개 이상.
- Dismiss stale pull request approvals when new commits are pushed: 코드 변경 후 재검토.
- Require conversation resolution before merging: 리뷰 미해결 대화 해결.
- Restrict who can push to matching branches: main 갱신 권한을 팀장으로 제한. 작업 브랜치는 제한 대상에서 제외.
- Do not allow bypassing the above settings: 팀장도 PR·승인 규칙 준수.
- force push와 main 삭제 금지. 병합 완료한 작업 브랜치 삭제는 가능.

조직 ruleset을 사용하는 경우 같은 효과가 되도록 관리자가 확인합니다. 팀장을 PR 우회 허용자로 등록하여 리뷰를 생략하지 않습니다. 자동 병합이나 merge queue 구성은 요구하지 않습니다.

공개 범위·요금제·조직 정책상 기능이 제공되지 않으면 **적용 불가 항목과 팀장만 병합하는 운영 규칙**을 기록하고 공유합니다. 기술적으로 차단했다고 적지 않으며, 임의로 공개 전환하거나 요금제를 바꾸지 않습니다.

작은 문서 PR로 **승인 전 병합 불가 → 타인 승인 → 팀장 병합**을 확인하고 설정 화면과 PR 링크를 남깁니다. 기존 main 이력을 지우거나 강제 push하여 시험하지 않습니다.

#### 작업 순서

**Issue → 작업 브랜치 → 구현·시험 → PR → 리뷰·수정 → 팀장 병합 → main 동기화**

- Issue에 담당자·완료 조건을 적습니다. 예: 미검출 시 z=0 발행 및 정지 검증.
- 최신 main에서 feat/target-detection, fix/lost-stop, docs/run-guide처럼 작업별 브랜치를 만듭니다.
- PR의 base는 main, compare는 본인 브랜치로 선택하고 팀장에게 리뷰를 요청합니다.
- 실행 전 작업은 Draft PR로 공유할 수 있습니다. 제출 상태는 실제 검증 결과에 맞춥니다.
- 수정은 같은 브랜치에 커밋하고, 리뷰 대화에 변경 내용과 확인 결과를 남깁니다.
- 팀장이 조건 충족을 확인한 뒤 Squash and merge 방식으로 병합하는 것을 권장합니다.
- 병합 후 각자 최신 main을 내려받고 다음 작업은 새 브랜치에서 시작합니다.

같은 라즈베리파이 작업 폴더에서 네 명이 동시에 브랜치를 바꾸지 않습니다. 개인별 clone 폴더를 사용하고 하드웨어 통합 시험은 한 사람씩 수행합니다.

**PR 본문에 적을 내용**

1. 연결한 Issue와 완료 조건.
2. 무엇을 왜 바꿨는지.
3. 실제 실행 명령·시험 조건·로그 또는 이미지.
4. 토픽·단위·설정·실행 순서 변경 여부.
5. 남은 문제·장비 미확인 항목.

**코드 리뷰와 병합 기준**

| 항목 | 확인할 내용 |
| --- | --- |
| 요구사항 | Issue 완료 조건을 충족하는가 |
| 인터페이스 | 타입·단위·부호·시간 기준이 합의와 같은가 |
| 실패 처리 | 미검출·입력 중단·모터 통신 중단에서 정지하는가 |
| 제어 제한 | 속도·위치 제한과 변환이 올바른가 |
| 검증 | 실제 시험 조건·로그가 있고 미확인 상태가 표시되는가 |
| 재현 | 개인 경로·비밀정보 없이 README와 설정으로 실행 가능한가 |

리뷰는 ‘확인했습니다’로 끝내지 않고 **확인한 파일·조건·결과**를 남깁니다. 수정 필요 시 Request changes, 충족 시 Approve를 사용합니다. 충돌 해결 시 양쪽 작성자의 의도를 확인합니다. CI 구축은 필수가 아니지만 실행 확인 기록은 필수입니다.

### 평가 및 최종 시연 안내

단일 FPS·RMSE 수치를 모든 장비에 일괄 합격선으로 적용하지 않습니다. 조건의 일관성·실제 동작·실패 처리·결과 해석·재현 증거를 확인합니다. 기능 수를 늘리는 것만으로 심화를 충족하지 않습니다.

협업 평가에서는 팀 공통 결과와 각 수강생의 설명·구현·시험·리뷰를 함께 확인합니다. 저장소 생성, 팀장 책임, PR 리뷰와 병합 절차는 이번 팀 프로젝트의 필수 수행 항목입니다.

**권장 5분 시연**

프로젝트 마지막 날, 팀 별로 직접 기능을 구동해보는 시연을 진행하게 됩니다. 

| 순서 | 시간 | 내용 |
| --- | --- | --- |
| 목표와 구성 | 30초 | 대상·장비·노드 연결 |
| 정상 추적 | 1분 | 좌우 이동과 응답 |
| 소실·복귀 | 1분 | 가림 시 정지, 시야 내 재등장 복귀 |
| 정량 결과 | 1분 | Kp 비교, FPS·검출률·RMSE·복구 |
| 재현·협업 | 1분 | bag 재처리, 실행 확인, 4인 기여 |
| 한계 | 30초 | 실패 조건과 개선 방향 |

현장 시연이 실패하면 원본 영상·로그로 마지막 확인 상태와 실패 원인을 설명합니다. 
녹화는 녹화임을 표시합니다.

# 8️⃣ 참고 및 주의사항

### **참고 및 주의사항**

- 인지와 제어를 따로 성공시키는 데서 끝내지 말고 연결된 시스템을 검증합니다.
- 검출 실패, 입력 중단, 제어 통신 중단을 분리하고 각 정지 동작을 확인합니다.
- 반복 시험은 동일 조건으로 수행하고 실패·시간 초과 회차도 남깁니다.
- 오차·명령·측정 위치를 구분하고 모든 값에 단위·시간 기준을 적습니다.
- bag 재생 중 기록된 명령을 실제 모터에 재전송하지 않습니다.
- PR 승인 후 내용이 달라지면 재검토합니다. 팀장도 승인·검증 규칙을 우회하지 않습니다.
- 자료 링크만 남기지 말고 기준 버전·사용 구간·재현 방법까지 기록합니다.
